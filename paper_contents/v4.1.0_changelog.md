# v4.1.0 变更日志

**分支**：`final_paper_experiments`（从 `add_states` 分支 `v4.0.0_final_1` 切出）
**目的**：修复代码审计发现的"死代码惩罚"bug，并跑一组缩小规模的补充实验验证修复效果，不替换、不动 `v4.0.0_final_1` 的冻结结果。

---

## 背景：发现了什么问题

在核对 `各算法伪代码.md` / `formula.md` 描述的公式与实际代码是否一致时，发现 `ppo_mask`、`ppo_lagrangian`、`ppo_opt`、`dqn`、`ddqn` 五个算法（`ppo` P3无约束基线除外）的 `env.py::step()` 里，都计算了一个"违规/修复惩罚"局部变量，但从未真正加进返回给智能体的 `reward` 里——非终端步的 `reward` 实际上恒为 `0.0`。也就是说，这些算法在 v4.0.0 训练时，逐步（per-step）层面对违规行为**没有任何真实生效的负反馈**，唯一起作用的是终局（episode结束时）的分级奖励公式。

进一步核对时又发现一个更深的问题：`ppo_lagrangian` 的 `env.py` 里定义了 `action_masks()` 方法，但其 `run_all.py` 用的是普通 `PrunedPPO`（`stable_baselines3.PPO` 子类），**从未用 `ActionMasker`/`MaskablePPO` 包装环境**——`action_masks()` 是完全没被调用过的死代码。经与用户确认，**这不是bug，是设计意图**：硬掩码是 `ppo_mask`(P4) 独有的机制，`ppo_lagrangian`(P5) 的方法论意义就是"用惩罚/对偶变量代替掩码"，如果P5也硬掩码就和P4没区别了。此前 `lt`/`eq` 场景的文档已经写对了（或接近准确），但 **`lt` 场景的docstring** 错误地写成"Hard capacity (masked)"，需要订正为准确描述。

再进一步发现 **`gt` 场景的 `ppo_lagrangian`** 与 `lt`/`eq` 不是同一套机制：`gt` 的 `step()` 内部有一段真实的重定向逻辑（`mask = self.action_masks(); if not mask[action]: 重定向到剩余容量最大的合法ECU`），会在容量违规时把动作事后纠正到一个可行ECU上，效果类似 `ppo_opt` 的repair机制。这与 `lt`/`eq`（容量违规只给固定惩罚，动作不做任何纠正）不一致，属于历史遗留的跨场景实现漂移。经与用户确认，**予以删除**，让三场景的 `ppo_lagrangian` 机制完全对齐（都是"无结构性约束保证，只有固定/自适应惩罚"）。

## 代码改动清单

### 1. 死代码惩罚接入 reward（5算法 × 3场景，共14个文件；`eq/ppo_mask` 例外见下）

| 文件 | 改动前（非终端步） | 改动后（非终端步） |
|---|---|---|
| `scenarios/{lt,eq,gt}/dqn/env.py` | `reward = 0.0` | `reward = cap_penalty + conflict_penalty`（gt场景无独立cap_penalty变量，见下） |
| `scenarios/{lt,eq,gt}/ddqn/env.py` | `reward = 0.0` | 同dqn |
| `scenarios/{lt,gt}/ppo_mask/env.py` | `reward = 0.0` | `reward = violation_penalty`（仅强制溢出兜底时非零） |
| `scenarios/{lt,eq,gt}/ppo_lagrangian/env.py` | `reward = 0.0` | `reward = step_reward/match_gain + cap_penalty + lagrange_penalty`（完整接入docstring公式，含正向match_gain项，非仅补惩罚——这是用户明确要求的方案） |
| `scenarios/{lt,eq,gt}/ppo_opt/env.py` | `reward = 0.0` | `reward = repair_penalty` |

**例外：`eq/ppo_mask/env.py` 未改动**——该文件的 `action_masks()` 没有强制溢出兜底分支，代码里根本不存在 `violation_penalty` 这个变量，不属于本次bug范围，不应强行注入不存在的惩罚项。

`ppo`(P3无约束基线) **完全未改动**，作为设计上"什么都不管"的对照组，本来就不该有惩罚。

### 2. `ppo_lagrangian` docstring 订正（3个文件，lt/eq/gt）

统一订正为准确描述："P5 不使用任何动作掩码——硬掩码是P4专属机制；capacity 违规给固定 `-2.0` 惩罚；conflict 违规给拉格朗日自适应惩罚；`action_masks()` 方法保留但确认是死代码（从未被 `run_all.py` 调用）"。

### 3. `gt/ppo_lagrangian/env.py` 删除容量重定向逻辑

```diff
- # Hard capacity enforcement
- mask = self.action_masks()
- if not mask[action]:
-     valid = np.where(mask)[0]
-     if len(valid) > 0:
-         action = int(valid[np.argmax(self.remaining_vms[valid])])
-
  cap_violated      = bool(self.remaining_vms[action] < svc.requirement)
  conflict_violated = self._has_conflict(action, self._step)
- violated          = conflict_violated  # only conflict counts as violation now
+ violated          = cap_violated or conflict_violated
```

同时把之前"容量靠mask兜底，不需要独立惩罚"的 `match_gain = float(ru)  # no capacity penalty since mask enforces it` 改为补上 `cap_penalty = -2.0 if cap_violated else 0.0` 并纳入reward，与lt/eq的处理方式完全对齐。

### 4. 版本号

`shared/version_config.py::CURRENT_VERSION` 从 `"3.0.0"`（已过期未跟上实际版本）更新为 `"4.1.0"`。

### 5. 新增实验基础设施（未纳入此前git版本控制的脚本类别，本次起新增文件均纳入版本控制）

- `scripts/run_v4.1.0_2M_campaign.py`：3场景 × 3种子 × 6算法（含未修改的ppo基线）= 54次训练，统一2,000,000步预算（对比v4.0.0的5,000,000步/5种子），沿用与5M campaign相同的加权并发调度器。完成后自动调用报告生成器。
- `scripts/generate_v4.1.0_report.py`：读取campaign manifest，聚合每个(场景,算法)在3个种子上的 AR/success_rate/违规率 均值±标准差，与 `results/add_states/`（v4.0.0冻结结果）做方向性对比（非严格消融，因步数预算不同），输出到 `paper_contents/v4.1.0_reports/report_<时间戳>.md` 与 `latest.md`。

## 实验规模与前提说明

- **规模**：3场景(lt/eq/gt) × 3种子(1,2,3) × 6算法 = 54次训练，每次2,000,000步（缩小自v4.0.0的5,000,000步×5种子×3场景×6算法=90次）。
- **不是对v4.0.0_final_1的替换**：`add_states` 分支上的 `v4.0.0_final_1` 标签与全部数据原样保留，本次实验的结果落在 `results/final_paper_experiments/` 目录（按分支自动隔离，见 `shared/paths.py`），互不覆盖。
- **不是严格的"修复前后"消融**：由于同时改变了训练步数预算（5M→2M）和种子数（5→3），本次数据与v4.0.0的差异不能单纯归因于"reward修复"，报告中的v4.0.0对比列仅作方向性参考。若要做严格消融，需要在相同步数/种子预算下分别跑"修复前"和"修复后"两组，属于后续可选的更细致验证。

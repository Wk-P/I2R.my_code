# 各算法伪代码

本文档给出 6 个算法各自的**核心决策/约束处理机制**级伪代码（区别于 `论文概要3.md` 第十三节已有的"整体实验管线"和"单 episode 通用逻辑"伪代码——那部分讲的是所有算法共享的外层流程，这里讲的是每个算法在约束处理方式上的具体差异）。

伪代码直接对应 `scenarios/lt/{算法}/env.py` 与 `run_all.py` 的真实实现（以 lt 场景为准；三场景的 reward 公式本身是否统一见 `论文概要3.md` 12.6 节，这里描述的是约束处理**机制**，机制在三场景间是一致的，不同的只是 reward 公式的具体系数）。全部内容截至 2026-09-10（正式 5 种子 campaign 完成后），**实验不再改动**，本文档只做只读整理。

## PPO（P3，无约束 baseline）

用 `stable_baselines3.PPO`（非 Maskable 版本），动作空间是对 N 个 ECU 的无限制离散选择；环境虽然实现了 `action_masks()`（容量维度），但 `run_all.py` 从未用 `ActionMasker` 包装环境、也未传给 `MaskablePPO`，因此掩码方法只是留存的接口，训练时完全不生效。

```
for t = 1..M:
    a_t ← policy.sample(all N ECUs)          # 无任何约束限制,包括容量在内
    cap_violated      ← remaining_vms[a_t] < svc[t].requirement
    conflict_violated ← has_conflict(a_t, t)
    # 违规只记录计数,不影响本步是否能执行、也不改变本步reward
    ru ← svc[t].requirement / initial_vms[a_t]
    total_ru += ru                            # 即使违规,ru照常计入AR分子
    执行放置(a_t, svc[t])                      # 强制执行,允许remaining_vms变负/冲突共存
if t == M:
    reward ← 终局AR分级奖励(见12.3式),violations>0则退化为valid_placed比例惩罚
返回 episode是否成功(=violations==0), 最终AR
```

**关键点**：约束是否被满足只体现在 info 字典和最终 success 判定里，不体现在单步 reward、不限制动作空间——这是刻意设计的"什么都不管"下限基线，用来衬托其余 5 种算法各自处理约束的方式，其低 success_rate 是设计使然（见五种子 campaign 结果：lt 场景 success_rate 仅 35.0%）。

## PPO+Mask（P4，硬掩码）

用 `sb3_contrib.MaskablePPO` + `ActionMasker` 包装环境；env 提供 `action_masks()`，采样前把不可行动作的概率直接置零（而不是采样后惩罚）。

```
def action_masks(state):
    svc ← services[t]
    base_mask[j] ← (remaining_vms[j] >= svc.requirement) AND NOT has_conflict(j, t)   # 硬约束:容量+冲突
    if base_mask全False:
        return base_mask                       # 无路可退,交给环境事后判violation
    # 一步前瞻:在base_mask基础上,再排除"选了它必导致未来某个服务无处安放"的选项
    refined_mask[j] ← base_mask[j] AND NOT lethal_after(j)
    return refined_mask if refined_mask有True else base_mask   # 前瞻全灭时退回基础掩码,不留空掩码

for t = 1..M:
    mask ← action_masks()
    a_t ← policy.sample(仅mask=True的ECU)      # 采样空间被硬性限制,不可行动作概率强制为0
    执行放置(a_t, svc[t])                       # 由构造保证:只要mask非全False,该步不会违规
if t == M:
    reward ← 12.3式分级终局奖励(lt场景另含AR权重课程w与势函数塑形,见12.4)
```

**关键点**：约束处理发生在动作**采样之前**，是四种约束机制里唯一能做到"训练/部署阶段均理论上零违规"的方式（campaign 结果：lt/eq/gt 三场景 CapViol%=ConflictViol%=0.00%），代价是需要能穷举可行动作集合，且一步前瞻本身是启发式近似（不保证全局最优可行序列）。

## PPO+Lagrangian（P5，拉格朗日对偶软约束）

容量维度仍用掩码（硬约束，只允许容量够用的 ECU），冲突维度改为**拉格朗日对偶上升**动态调整的软惩罚，而非硬性禁止——`env.py` 注释明确标注"Hard capacity (masked), Lagrangian conflict (adaptive penalty)"。

```
初始化: λ ← LAMBDA_INIT, base_penalty ← 0.2, LAMBDA_LR, LAMBDA_TARGET, LAMBDA_MAX(=10.0)

# 环境内部(每一步):
for t = 1..M:
    a_t ← policy.sample(容量掩码限制的ECU集合)   # 冲突不掩码,仍可能选到冲突ECU
    c_t ← 1.0 if has_conflict(a_t, t) else 0.0    # 冲突违规指示量,不是连续惩罚
    match_gain ← svc[t].requirement / initial_vms[a_t]
    lagrange_penalty ← -(λ + base_penalty) * c_t  # 软惩罚,随λ增大而加重,不阻止选择
    forced_overflow_penalty ← -2.0 if cap_violated else 0.0  # 容量理论上被掩码避免,仅极端fallback触发
    total_ru += match_gain                        # 冲突不清零ru,靠λ惩罚抑制,而非直接扣AR
    step_reward ← match_gain/n_active + lagrange_penalty + forced_overflow_penalty
if t == M:
    reward ← 12.3式分级终局奖励(violations==0判定含冲突计数)

# 训练回调(LagrangeCallback,每隔LAMBDA_UPDATE_WINDOW个episode执行一次对偶上升):
avg_viol ← 该窗口内episode冲突违规率的滑动平均
λ ← clip(λ + LAMBDA_LR * (avg_viol - LAMBDA_TARGET), 0, LAMBDA_MAX)   # 对偶上升:违规多则λ增大、惩罚变重
env.set_lambda(λ)                                # 广播新λ给所有并行环境实例
```

**关键点**：这是四种约束机制里唯一维护真实对偶变量、按violation率做梯度式更新的方案（不是固定惩罚系数）；λ 只作用于冲突约束，容量约束仍是硬掩码——严格来说是"硬约束(容量)+软约束(冲突)"的混合方案，不是纯拉格朗日方法，写论文时需准确表述这一点，不能笼统写成"拉格朗日处理全部约束"。

## Repair PPO（P6，ppo_opt，启发式修复兜底）

策略在完全无约束的动作空间上采样；若选择违规，环境内部立即用 best-fit 启发式**重新指派**一个可行 ECU 顶替原动作，再继续往下执行——修复发生在 `env.step()` 内部，策略本身并不知道发生过修复（观测到的是修复后的结果）。

```
def best_fit_repair(svc_idx):
    svc ← services[svc_idx]
    valid ← {j : remaining_vms[j] >= svc.requirement AND svc_idx ∈ ecu_allowed[j]}   # 容量+冲突均满足
    if valid为空: return None                     # 无法修复
    return argmax_{j∈valid} (svc.requirement / initial_vms[j])   # best-fit:选剩余利用率最高的可行ECU

for t = 1..M:
    a_t ← policy.sample(all N ECUs)                # 无掩码,策略可以选任意ECU
    cap_violated      ← remaining_vms[a_t] < svc[t].requirement
    conflict_violated ← has_conflict(a_t, t)
    if cap_violated OR conflict_violated:
        a_repaired ← best_fit_repair(t)
        if a_repaired is None:
            返回 reward=-M, episode立即终止        # 无路可修,直接判负
        a_t ← a_repaired                           # 策略的原始动作被静默替换
        repairs += 1
    执行放置(a_t, svc[t])                           # 保证:只要能修复,这一步就不会真正违规
if t == M:
    reward ← 12.3式分级终局奖励(success = 全程未触发任何修复)   # 与ppo_mask/ppo/dqn/ddqn完全同一公式,无额外项
```

⚠**订正（2026-09-11）**：本节此前的版本写了 `repair_penalty ← -0.1`（触发修复时的单步惩罚）和 `terminal_bonus ← AR*(1-repair_rate)`（终局按修复率给的额外奖励），这两个是照 `env.py` 顶部的**设计文档字符串**转写的，但直接核对 `step()` 函数实际代码后发现：`repair_penalty` 和 `terminal_bonus`(实为 `step_reward`) 这两个局部变量都被计算了，但**从未被加进最终返回的 `reward` 里**——是写了却没接线的死代码，docstring 描述的设计意图和实际生效的奖励公式对不上。已核实 ppo_opt 实际使用的 `reward` 变量，与 ppo_mask/ppo_lagrangian/ppo/dqn/ddqn 完全同构：成功时 `M*(2·AR-1)`，失败时 `-M*(1-valid_placed/M)`，不含任何与"是否触发过修复"直接挂钩的惩罚或奖励项——也就是说策略完全没有单步层面的信号提示"这一步被修复了"，唯一能感知到修复影响的途径是修复本身可能改变了后续状态从而间接影响最终 AR。这与下面"关键点"里已经证实的现象（eq/gt 场景策略对约束毫不在意、大量依赖修复）完全吻合，甚至比先前设想的还要彻底——**代码里根本没有那个本该抑制这种行为的 -0.1 惩罚在起作用**，进一步解释了为什么策略在资源宽松场景下毫无顾忌地依赖修复。

**关键点**：真正"零违规"的保证来自环境内置的修复兜底，而不是策略学会了避让——五种子 campaign 里 lt 场景 CapViol%/ConflictViol% 为 24.30%/54.25%，eq/gt 场景则接近 100%。逐 episode 回放核实过（用保存权重+匹配的 TRAIN_SEED 重放，数字与 `summary.csv` 完全对上）：lt 场景成功的 episode 里 94.9% 全程未触发过一次修复，说明资源紧缺迫使策略学出了真正的约束规避能力；而 eq/gt 场景资源宽松、修复几乎不会失败，成功近乎"稳赚"，`-0.1` 的修复惩罚相对终局奖励微不足道，策略因此完全没有动力学真正的约束规避——eq 场景平均每个成功 episode 有约 7.7/10 步是靠修复兜住的。这不是训练失败或统计错误，而是策略对启发式修复机制的策略性利用（reward hacking）：资源越宽松，策略越"摆烂"、越依赖修复。这一点是论文里反复强调的"ppo_opt 的高成功率主要归功于环境修复机制，不能算策略自主学会约束满足"的代码与数据依据。

## DQN

标准 off-policy Q-learning，动作空间与 PPO 家族一致（离散选择 N 个 ECU 之一），无掩码、无修复、无对偶惩罚——约束处理方式与 plain PPO(P3) 同构：违规只记录，不限制动作、不额外惩罚，reward 公式与 12.3 式相同（分级终局奖励）。

```
初始化: replay_buffer, q_net, q_net_target ← copy(q_net)
for env_step = 1..TOTAL_STEPS:
    a_t ← epsilon_greedy(q_net, obs_t)             # 探索期内按DQN_EXPLORATION_FRACTION衰减
    obs_{t+1}, r_t, done ← env.step(a_t)           # env与P3同款:违规不惩罚,只记录
    replay_buffer.add(obs_t, a_t, r_t, obs_{t+1}, done)
    if step % TRAIN_FREQ == 0:
        batch ← replay_buffer.sample(BATCH_SIZE)
        target_q ← r + (1-done) * gamma * max_a' q_net_target(obs_{t+1}, a')   # 标准DQN:target网络自己选也自己评估
        loss ← smooth_l1(q_net(obs_t, a_t), target_q)
        梯度下降更新 q_net
    if step % TARGET_UPDATE == 0:
        q_net_target ← copy(q_net)
```

## DDQN

继承 `stable_baselines3.DQN`，只重写 `train()` 方法里 target Q 值的计算方式（Double DQN，van Hasselt et al. 2016），其余（探索策略、replay buffer、环境、reward）与 DQN 完全一致，是控制变量下唯一的差异点。

```
class DDQN(DQN):
    def train(gradient_steps, batch_size):
        for _ in range(gradient_steps):
            batch ← replay_buffer.sample(batch_size)
            # 与DQN的唯一区别:动作选择和价值评估解耦到两个不同网络
            best_actions ← argmax_a' q_net(obs_{t+1}, a')          # 用在线网络选动作(而非target网络)
            next_q       ← q_net_target(obs_{t+1})[best_actions]   # 用target网络只评估该动作的价值
            target_q ← r + (1-done) * gamma * next_q
            loss ← smooth_l1(q_net(obs_t, a_t), target_q)
            梯度下降更新 q_net
        # target网络同步频率、探索策略、环境约束处理均与DQN相同
```

**关键点**：DQN 用 `q_net_target` 同时完成"选动作"和"评估价值"两件事，容易高估 Q 值；DDQN 把"选动作"交给在线网络 `q_net`、"评估价值"交给 `q_net_target`，解耦两个角色以抑制过估计偏差——这是 DQN/DDQN 唯一的代码级差异，动作空间、状态空间、约束处理方式（均无掩码/无修复/违规不惩罚）与环境本身在两者之间完全共享。

## 六算法约束处理机制一览

| 算法 | 动作空间是否受限 | 约束处理时机 | 违规是否可能发生 | 训练/部署零违规保证 |
|---|---|---|---|---|
| PPO (P3) | 否，全空间自由采样 | 无——只记录 | 是，且不修正 | 无 |
| PPO+Mask (P4) | 是，采样前硬掩码(容量+冲突+一步前瞻) | 采样前 | 理论上否(mask非全False时) | 有(结构性保证) |
| PPO+Lagrangian (P5) | 部分——容量硬掩码，冲突不掩码 | 容量:采样前；冲突:事后软惩罚+对偶上升调整λ | 冲突可能发生(软约束) | 无严格保证，靠训练收敛后λ抑制到低violation率 |
| Repair PPO (P6/ppo_opt) | 否，全空间自由采样 | 事后：环境内 best-fit 重新指派 | 策略动作本身常违规，但被静默修复 | 有条件保证(修复失败时判负) |
| DQN | 否，全空间自由采样 | 无——只记录 | 是，且不修正 | 无 |
| DDQN | 否，全空间自由采样 | 无——只记录(与DQN共享环境) | 是，且不修正 | 无 |

以上机制描述与 `论文概要3.md` 十二/十三节的公式/流程级伪代码互为补充：十二/十三节讲"reward 怎么算、整条实验管线怎么跑"，本文档讲"每个算法在动作/约束层面到底做了什么"。

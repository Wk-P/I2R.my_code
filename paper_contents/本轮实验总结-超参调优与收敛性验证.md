# 本轮实验总结:超参调优、网络结构、收敛性验证

本文档汇总一轮较长的实验探索过程中产出的、与论文相关的技术事实、数据和最终决策。**只记录事实和数据,不涉及论文的论证方式或叙事框架**(由作者自行撰写)。

---

## 1. 背景:为什么要做这一轮验证

论文原本的正式实验(`scripts/run_full_5M_campaign.py`)采用"6算法×3场景,统一5M步预算"的设计,以保证跨算法对比公平。但在检查过程中发现两个问题:

1. **超参数存在场景间不一致**:`ppo_opt` 的 `ent_coef` 在 eq 场景被设为 0.005,但 lt/gt 场景从未设置过(默认吃 SB3 的 0.0)——同一算法在不同场景用了不同的隐藏配置,污染了跨场景对比。
2. **网络结构从未做过深度实验**:此前只测过宽度(256×256 vs 64×64 等),从未测试层数(2层 vs 3层 vs 4层)。

因此启动了一轮系统性的:超参数搜索 → 网络结构搜索 → 多预算量级交叉验证 → 收敛性验证。

---

## 2. 方法论:核心教训(可用于论文的方法论章节)

### 2.1 短预算超参数搜索的排序不可靠

- 用 200k 步(4%正式预算)做超参数搜索,选出的"最优"配置,拿到 1M 步复核后排序会反转;拿到 1M 步选出的"最优",再拿到 5M 步复核,排序又可能反转。
- 典型案例:`ppo_mask` 在 200k/1M 步搜索中,某候选配置看起来比基线更好,但在 5M 步的正式对照中,候选配置在 lt 场景反而明显更差(-0.115)。
- **结论**:任何短于正式训练预算的超参数搜索,其排序结果都不能直接采信,必须在正式预算下用"候选 vs 基线"的头对头对照来确认,不能只看候选自己的数字变化趋势。

### 2.2 On-policy vs Off-policy 的收敛速度差异巨大

- PPO 家族(ppo/ppo_opt/ppo_mask/ppo_lagrangian)在 500k~1M 步就基本进入平台期,5M 步的训练预算对它们绰绰有余。
- DQN/DDQN(off-policy,基于 replay buffer)如果用了"激进"的候选超参数(小网络+大 buffer),需要 15-20M 步才能接近平台期,5M 步只能达到最终水平的 30%-50%。但用**实际保留的默认超参数**(网络 [128,128]、buffer=100k)重新验证时,5M~7M 步就已经进入噪声带内的平台期——说明是超参数本身的问题,不是算法结构决定的。
- **一个被推翻的经典误判**:`gt/ddqn` 早期用某组超参数在 5M 步的单点快照 success_rate 只有 0.175,远低于同场景其它算法,一度被怀疑是"超参数不适配 gt 场景"。用收敛曲线复核后发现,这组超参数在该场景本身就没训完(5M 步时还在爬坡),真实平台期数值在 0.77~0.94 之间——**纯粹是训练未完成造成的假象,不是算法或场景的问题**。

### 2.3 单点快照 vs 收敛曲线

- 单一预算下的单一 success_rate 数字,无法判断"训练是否已经收敛"。同一份数据,曲线的最后几个检查点如果还在系统性上升,说明还没训完;如果只是在一个区间内噪声波动(没有净增长趋势),才能认为已经收敛。
- 本轮为此实现了一个轻量的"收敛探针"机制:训练过程中每隔固定步数在一个小样本子集上评估一次 success_rate/AR,产出完整轨迹,而不是只在训练结束时评估一次。

## 3. 最终决策:6 算法 × 3 场景

| 算法 | 是否调整 | 依据 |
|------|---------|------|
| **ppo_opt** | ✅ **已采纳新配置**,写入 `scenarios/{lt,eq,gt}/ppo_opt/config.py` | 200k/1M/5M 三档预算 + lt/eq/gt 三场景一致胜出;收敛曲线确认 lt 场景 500k~1M 步进入平台期(0.34~0.51 区间),eq/gt 达到 1.0 封顶 |
| ppo_mask | 维持现状,不改动 | 候选配置(3层网络+ent_coef=0.02)在 5M 步头对头对照中,lt 场景明显更差(-0.115),eq/gt 打平(都封顶 1.0),没有采纳理由 |
| ppo_lagrangian | 维持现状,不改动 | 候选配置在 5M 步对照中三场景均未见提升(-0.0025 ~ -0.02) |
| ppo(基础版,P3) | 维持现状,未深入调参 | 该算法是刻意设计的"无约束 baseline"(容量/冲突约束只记录不惩罚,reward=终局AR),其低 success_rate 是奖励函数设计决定的天花板,超参数调整无法弥补这个结构性限制,调参优先级低 |
| dqn | 维持现状,不改动超参数 | 独立搜索(修复了与ddqn共享随机种子的bug后重新搜)出的候选(net_arch=[64,64], buffer=500k)在 5M 步对照中全场景落败于旧默认配置 |
| ddqn | 维持现状,不改动超参数 | 候选(net_arch=[64,64], buffer=1M)5M步对照:lt更差,eq/gt更好但差距小,综合不采纳,优先保留 lt(论文重点困难场景)上的优势 |
| **训练预算** | 统一 **5M 步**,6算法×3场景一致 | 详见下表 |

### ppo_opt 新配置(已生效)

```
PPO_LR         = 1e-4      (原 3e-4)
PPO_N_STEPS    = 1024      (原 512)
PPO_BATCH_SIZE = 64        (原 256)
PPO_N_EPOCHS   = 20        (原 10)
PPO_CLIP_RANGE = 0.3       (原 0.2)
PPO_ENT_COEF   = 0.001     (原:lt/gt未设置即0.0;eq为0.005，三场景现已统一)
PPO_NET_ARCH   = [256, 256, 256]   (原 [256, 256]，2层→3层)
```

网络深度实验发现:**更深的网络(3~4层)对 PPO 家族普遍有提升**(ppo_opt 在 lt 场景 test_success 从 0.19 提升到 0.25,+30%相对提升),且训练/测试 gap 没有变大(不是过拟合)。

DQN 家族的网络结构实验则相反:**更小的网络([64,64])往往优于默认的 [128,128]**,更深的网络(3~4层)反而普遍更差——这是 PPO(on-policy 策略梯度)与 DQN(off-policy Q-learning)在网络容量敏感性上的一个有意思的对比,可能与 Q 值估计在大网络下更不稳定有关。不过这组候选最终在 5M 步头对头对照中没有胜过旧默认配置,所以**没有被采纳**,仅作为方法论发现记录。

### 训练步数配置(`shared/training_steps_config.py`)

统一为:

```python
SCENARIO_TOTAL_STEPS = {
    (scenario, algo): 5_000_000
    for scenario in ("lt", "eq", "gt")
    for algo in ("ppo_mask", "ppo_lagrangian", "ppo", "ppo_opt", "dqn", "ddqn")
}
```

(中途曾短暂把 dqn/ddqn 单独调到 15M 步,后经过用"实际保留配置"重新验证收敛性,确认 5M 步即可,改回统一预算——过程见第 2.2 节。)

## 4. 收敛性全面验证:18 组合完整结果

用**各场景实际保留的配置**(不是候选配置),每个组合跑到 6M 步(比 5M 多留 1M 余量),每 25 万步评估一次,得到完整学习曲线。下表是 5M~6M 步区间的数值范围(可理解为"平台期噪声带"):

| 算法 \ 场景 | lt | eq | gt |
|------|-----|-----|-----|
| ppo | 0.31–0.40 | 0.77–0.87 | 0.93–0.99 |
| ppo_opt | 0.40–0.51 | **1.00(封顶)** | **1.00(封顶)** |
| ppo_mask | 0.52–0.59 | **1.00(封顶)** | **1.00(封顶)** |
| ppo_lagrangian | 0.46–0.62 | 0.88–0.94 | 0.97–1.00 |
| dqn | 0.42–0.48 | 0.69–0.83 | 0.75–0.96 |
| ddqn | 0.34–0.46 | 0.69–0.83 | 0.77–0.94(此前的"0.175异常"已被推翻,见2.2节) |

**结论**:全部 18 个组合在 5M~6M 步区间都表现为"围绕一个中枢值的噪声波动",没有一个存在持续上升趋势——统一 5M 步预算对全部 6 算法 × 3 场景成立。eq/gt 场景数值普遍偏高且方差小,是因为这两个场景问题相对简单(多数算法轻松封顶或接近封顶),真正有区分度、能看出算法/超参数差异的是 **lt 场景**(资源紧缺,论文的核心困难场景)。

## 5. 其它方法论发现(可能与论文叙事相关)

- **ILP 与 RL 的计算耗时对比**(wall-clock vs CPU-time)结论不单一:
  - Wall-clock 下,ILP 与 PPO 家族耗时接近,DQN/DDQN 明显更快(约 7 倍)。
  - CPU-time(把多线程占用的核数都算进去)下,PPO 家族反而比 ILP 贵 5~9 倍(torch 默认多线程在小网络上的开销),只有 DQN/DDQN 仍然更快。
  - ILP 求解耗时随问题规模(N/M)增长呈现远超线性的增长(N=10→30,耗时暴涨约200倍),支持"NP-hard 问题规模增长时 RL 推理开销增长更平缓"这一论点,但需要在正式实验里补充更多规模点的重复采样才能写成严谨的图表。
- **代码里 numpy 的使用**:环境类(`env.py`)里逐元素的可行性/冲突判断逻辑,大部分仍是 Python 循环 + 最后包一层 `np.array()`,并没有真正用上 numpy 的向量化能力。但当前问题规模(N=10, M=15)太小,向量化本身的收益有限,不建议现阶段优化;如果论文/后续工作要扩展到更大规模,这里会成为真正的瓶颈。
- **plain ppo(P3)的设计**:约束(容量/冲突)只记录不惩罚,reward 只有终局 AR,没有任何 shaping。这个"什么都不管"的 baseline 用来衬托 ppo_mask(硬掩码)/ppo_opt(修复+shaping)/ppo_lagrangian(软惩罚)等方法处理约束的效果,其低 success_rate 是设计使然,不是训练不充分。

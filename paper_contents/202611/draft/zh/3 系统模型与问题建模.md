# 3 系统模型与问题建模（中文对照版）

> 本文件是英文正文 `../3 System Model and Problem Formulation.md` 的中文对照，供核对内容。以英文版为准，修改时两边同步。

本章定义本文研究的服务部署问题。3.1 节介绍系统模型和符号；3.2 节给出整数线性规划（ILP）模型及作为参照基准的精确求解方法；3.3 节说明隐私冲突约束。隐私冲突是硬约束，也是第 4 章采用安全强化学习框架的原因。

## 3.1 系统模型

考虑一个边缘计算系统，包含 $N$ 个边缘计算单元（ECU）和 $M$ 个待部署的服务。每个 ECU $n \in \{1,\dots,N\}$ 的资源容量为 $c_n$，每个服务 $m \in \{1,\dots,M\}$ 的资源需求为 $e_m$。每个服务必须恰好部署在一个 ECU 上；只要 ECU 上部署了至少一个服务，就称它为*已启用*。

有些服务不能共用同一个 ECU，因为部署在一起会带来隐私风险。参照 \cite{xu2020trust}，这种关系用 $K$ 个隐私冲突集 $C_1,\dots,C_K \subseteq \{1,\dots,M\}$ 描述：同一冲突集中的任意两个服务必须部署在不同的 ECU 上。

部署决策用两组二元变量描述：

$$
x_{mn} =
\begin{cases}
1, & \text{服务 } m \text{ 部署在 ECU } n \text{ 上}\\
0, & \text{否则}
\end{cases}
\qquad
y_n =
\begin{cases}
1, & \text{ECU } n \text{ 已启用}\\
0, & \text{否则}
\end{cases}
$$

符号汇总见表 3.1。

**表 3.1** 符号。

| 符号 | 含义 |
|---|---|
| $N$, $M$ | ECU 数、服务数 |
| $n \in \{1,\dots,N\}$ | ECU 下标 |
| $m \in \{1,\dots,M\}$ | 服务下标 |
| $c_n$ | ECU $n$ 的容量 |
| $e_m$ | 服务 $m$ 的资源需求 |
| $C_k$，$k = 1,\dots,K$ | 隐私冲突集 |
| $x_{mn} \in \{0,1\}$ | 服务 $m$ 是否部署在 ECU $n$ |
| $y_n \in \{0,1\}$ | ECU $n$ 是否启用 |

目标是高效利用边缘资源。本文采用 \cite{xu2020trust} 的*平均资源利用率*（AR），即所有已启用 ECU 利用率的平均值：

$$
\text{AR}(x, y) = \frac{F(x)}{G(y)},\qquad
F(x) = \sum_{m=1}^{M}\sum_{n=1}^{N} x_{mn}\,\frac{e_m}{c_n},\qquad
G(y) = \sum_{n=1}^{N} y_n .
$$

例如，启用 2 个 ECU，利用率分别为 0.9 和 0.5，则 $\text{AR} = 0.7$。AR 越高，说明启用的 ECU 越少、每个 ECU 装得越满。

## 3.2 整数线性规划模型

服务部署问题建模如下：

$$
\begin{aligned}
\max_{x,\,y}\quad & \text{AR}(x, y) = \frac{F(x)}{G(y)} \\
\text{s.t.}\quad
&\textstyle\sum_{n=1}^{N} x_{mn} = 1, && \forall m && \text{(C1)}\\
&\textstyle\sum_{m=1}^{M} e_m\, x_{mn} \le c_n\, y_n, && \forall n && \text{(C2)}\\
&x_{mn} \le y_n, && \forall m, n && \text{(C3)}\\
&\textstyle\sum_{m \in C_k} x_{mn} \le 1, && \forall k, \forall n && \text{(C4)}\\
&x_{mn},\, y_n \in \{0, 1\}, && \forall m, n && \text{(C5)}
\end{aligned}
$$

(C1) 要求每个服务恰好部署一次。(C2) 是容量约束：一个 ECU 上所有服务的需求之和不能超过其容量，未启用的 ECU 不能部署服务。(C3) 把部署和启用联系起来。(C4) 是隐私冲突约束，见 3.3 节。(C5) 规定所有变量为二元变量。(C1) 和 (C2) 合在一起，也保证了系统的全部需求都能被满足。模型共有 $MN + N$ 个二元变量和 $M + N + MN + KN$ 个约束。

**用 Dinkelbach 方法精确求解。** AR 是两个线性函数之比，不能直接交给线性求解器。本文采用 Dinkelbach 方法 \cite{dinkelbach1967nonlinear}：把分式目标换成一系列线性目标的参数化 ILP，约束 (C1)–(C5) 保持不变：

$$
\varphi(\rho) = \max_{(x,y)\ \text{可行}} \big[\, F(x) - \rho\, G(y) \,\big].
$$

记最优 AR 为 $\text{AR}_{\text{ILP}}$。由于每个可行解都满足 $G(y) \ge 1$，所以 $F(x) - \rho G(y) > 0$ 当且仅当 $\text{AR}(x,y) > \rho$。因此 $\varphi(\rho) > 0$ 当且仅当 $\rho < \text{AR}_{\text{ILP}}$，$\varphi(\rho) = 0$ 当且仅当 $\rho = \text{AR}_{\text{ILP}}$。迭代步骤：

1. 令 $\rho_0 = 0$。
2. 把 $\varphi(\rho_t)$ 求解到最优，得到 $(x_t, y_t)$。
3. 令 $\rho_{t+1} = F(x_t) / G(y_t)$。
4. 若 $|\rho_{t+1} - \rho_t| < 10^{-6}$，停止并输出 $\text{AR}_{\text{ILP}} = \rho_{t+1}$；否则回到第 2 步。

每轮得到的解都是可行的，$\rho_t$ 单调不降；可行解个数有限，所以迭代有限步内终止。实验中每个参数化 ILP 用 PuLP 调用 CBC 求解，平均 3.06 轮收敛。

**计算复杂度。** 先证明本问题是强 NP-hard 的。

**命题 1.** 服务放置问题的判定版本——"是否存在满足 $\text{AR}(x,y) \ge \rho$ 的可行放置？"——是强 NP 完全的。即使 $K = 0$ 且所有 ECU 容量相同，结论仍成立。

*证明.* 属于 NP：给定 $(x, y)$，可在 $O(MN + KN)$ 时间内检查约束 (C1)–(C5) 和 $F(x) \ge \rho\, G(y)$。

困难性：从装箱问题归约，装箱问题是强 NP 完全的 \cite{garey1979computers}。装箱实例由物品大小 $s_1, \dots, s_M \in \mathbb{Z}_{>0}$、箱容量 $B \ge \max_m s_m$ 和整数 $k$ 组成，问能否用不超过 $k$ 个箱子装下全部物品。构造放置实例：$N = M$ 个容量均为 $c_n = B$ 的 ECU，需求 $e_m = s_m$，无冲突集（$K = 0$），阈值 $\rho = S / (kB)$，其中 $S = \sum_m s_m$。构造是多项式时间的，且数值原样复制，因此保持强 NP-hard 性。

容量相同时，任何满足 (C1) 的放置都有 $F(x) = \sum_m e_m / B = S / B$，于是

$$
\text{AR}(x, y) = \frac{S}{B\, G(y)},
$$

只取决于启用的 ECU 数。因此 $\text{AR}(x,y) \ge \rho \iff G(y) \le k$。若物品可装入不超过 $k$ 个箱子，则把第 $j$ 个箱子的物品放到 ECU $j$、只启用非空的箱子，即得 $G(y) \le k$ 的可行放置（$N = M$ 个 ECU 总是够用）；反之，$G(y) \le k$ 的可行放置中，每个启用 ECU 上的服务由 (C2) 构成一个合法的箱子。所以装箱实例为"是"当且仅当放置实例为"是"。$\square$

因此，除非 P = NP，否则该优化问题不存在多项式或伪多项式时间的精确算法。隐私冲突（$K > 0$）只会增加约束；而且 $K > 0$ 时，连"是否存在可行放置"都包含图着色作为特例（所有 $c_n$ 足够大、每条边一个冲突集）。最坏情况下 ILP 的搜索空间以 $N^M$ 增长，而且每一轮 Dinkelbach 迭代都要搜索一次。正因为代价这么高，本文用学到的策略代替在线精确求解。

**ILP 在本文中的作用。** ILP 不用于训练强化学习智能体，也不提供监督标签。它只用于：(i) 筛选问题实例，只保留求得最优解的实例，保证每个实例都可行；(ii) 评估学到的策略，以 $\text{AR}_{\text{ILP}}$ 作为最优性差距的参照（5.2 节）。

## 3.3 隐私冲突约束

在边缘计算中，处理敏感数据的服务如果运行在同一物理节点上，可能通过共享内存、共享存储或侧信道泄露彼此的信息。隐私泄露不能用更高的资源利用率来弥补，因此必须作为*硬*约束处理：违反隐私约束的部署方案无论 AR 多高都不可接受。

参照 \cite{xu2020trust}，隐私关系用冲突集 $C_k$ 建模。约束 (C4)

$$
\sum_{m \in C_k} x_{mn} \le 1, \qquad \forall k,\ \forall n
$$

表示每个冲突集在任何一个 ECU 上至多部署一个服务。换句话说，属于同一冲突集的两个服务绝不能部署在一起。为了方便第 4 章的顺序决策过程，把冲突集表示成对称的冲突图 $A \in \{0,1\}^{M \times M}$：$A_{mk} = 1$ 当且仅当 $m \ne k$ 且服务 $m$、$k$ 同属某个冲突集。

隐私冲突约束让问题比单纯的容量装箱难得多。容量违约只取决于 ECU 上的需求总量；冲突则不管 ECU 剩余容量多大，都会把它排除在某个服务的候选之外。本文的实验设置中（$K = 10$ 个冲突集，两两冲突概率 $p = 0.6$，见 5.1 节）冲突很密集。一连串单独看来合理的部署，可能让后面的某个服务找不到既装得下又无冲突的 ECU，这种状态称为*死局*。所有测试实例都已保证可行，所以死局一定是前面的部署决策造成的。智能体如何避开或应对死局，是本文比较的几种约束处理策略之间的核心区别。

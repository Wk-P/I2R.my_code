# ILP AR 计算原理

本文说明报告中 **ILP AR** 的来源：优化问题的定义、精确求解方法（Dinkelbach 迭代）、实例生成与筛选，以及 ILP AR 和 gap 在报告中的计算方式。实现见 `src/shared/ilp_utils.py`（`solve_ilp_max_ar`）与 `src/paper_rl/data.py`。

## 1. 问题

把 M 个服务放到 N 个 ECU 上，每个服务恰好放一个 ECU。

| 符号 | 含义 |
|---|---|
| c_n | ECU n 的容量（容器数），取值 {50, 55, …, 195} |
| e_m | 服务 m 的需求（容器数），取值 {10, 15, …, 95} |
| C_k | 第 k 个隐私冲突集（K = 10 个），同一集合内的服务不能放在同一 ECU |
| x_mn ∈ {0,1} | 服务 m 是否放在 ECU n |
| y_n ∈ {0,1} | ECU n 是否被使用 |

场景规模：EQ N=10, M=10；GT N=15, M=10；LT N=10, M=15。

**目标 AR（平均 ECU 利用率）**：

    AR = F(x) / G(y)，  F(x) = Σ_m Σ_n x_mn · e_m / c_n，  G(y) = Σ_n y_n

即所有被使用 ECU 的利用率之和除以被使用的 ECU 数。

**约束**：

1. 每个服务恰好放置一次：Σ_n x_mn = 1，∀m
2. 容量：Σ_m x_mn · e_m ≤ c_n · y_n，∀n（同时保证未开启的 ECU 不能放服务）
3. 开启关联：x_mn ≤ y_n，∀m, n
4. 隐私冲突：Σ_{m∈C_k} x_mn ≤ 1，∀k, ∀n

约束 4 对每个冲突集、每个 ECU 只允许最多一个成员，等价于"同一冲突集中的任意两个服务不同放"。

## 2. 为什么不能直接解一次 ILP

AR 是两个线性式之比（分式目标），不是线性目标，不能直接交给 ILP 求解器。

旧做法 `solve_ilp` 只最大化分子 F（总利用率），再除以使用的 ECU 数。但每个服务必放，所以 F 主要受"把服务放到小容量 ECU 上"驱动，并不会去减少开启的 ECU 数，得到的不是 AR 最优。在 v4.3.1.4 数据上它比真正最优低 0.07–0.12。自 v4.3.1.7 起一律改用 `solve_ilp_max_ar`；数据集中的 ILP AR 字段（`ar_star`）也已用 `src/scripts/recompute_ar_star.py` 重算。

## 3. Dinkelbach 迭代（精确求最大 AR）

对参数 λ 定义参数化 ILP：

    φ(λ) = max_{x,y 可行}  F(x) − λ · G(y)

关键性质：设最优 AR 为 λ_opt，则

- λ < λ_opt 时 φ(λ) > 0；λ = λ_opt 时 φ(λ) = 0；λ > λ_opt 时 φ(λ) < 0。
- 因为 G ≥ 1，φ(λ) 关于 λ 严格单调递减。

迭代过程：

1. λ₀ = 0。
2. 用 CBC（PuLP 默认的 MILP 求解器）求解 φ(λ_t)，得到可行解 (x_t, y_t)。
3. 令 λ_{t+1} = F(x_t) / G(y_t)，即这个解的实际 AR。
4. 若 |λ_{t+1} − λ_t| < 10⁻⁶，停止，输出 λ_{t+1} 和对应放置方案；否则回到 2（最多 30 轮）。

每轮得到的都是可行解，所以 λ_t 单调不降；只有当不存在 AR 更高的可行解时 λ 才不再变化，此时 φ(λ) = 0，λ 就是全局最优 AR。迭代次数有限（可行解有限），实际通常几轮内收敛。每轮的子问题都由 CBC 求到证明最优（状态 `Optimal`），所以最终结果是精确最优，不是启发式近似。

## 4. 实例生成与筛选

- ECU 容量、服务需求按上表取值独立均匀抽取。
- 冲突集：K = 10 个集合，每个服务以概率 q 独立加入每个集合，成员少于 2 的集合丢弃。任意两个服务冲突的概率 p = 1 − (1 − q²)^K，正式实验 p = 0.6。
- 每个实例都用 `solve_ilp_max_ar` 求解；状态不是 `Optimal`（无可行解）就整体重抽。因此**数据集里每个实例都存在满足全部约束的放置方案，且已知其最优 AR**。

使用的数据：

| 用途 | 来源 | 数量 |
|---|---|---|
| 训练 | `results/sup_diag/<场景>.json`（同一生成器，p = 0.6，全部经 ILP 求解为 Optimal） | 每场景 5 万 |
| 测试 | `data/v4.3.1.4/<场景>.yaml` 的 2000 个实例，按种子打乱后取 20% | 每个种子 400 |

`data/v4.3.1.4` 全部 2000 个实例的统计：

| 场景 | 平均 ILP AR | 最优解平均开启 ECU 数 |
|---|---|---|
| EQ | 0.858 | 5.88 |
| GT | 0.910 | 5.91 |
| LT | 0.880 | 7.96 |

测试集随种子划分，所以同一场景不同种子的 ILP AR 略有不同（例如 EQ：种子 2 为 0.860，种子 3 为 0.858）。

## 5. 报告中的 ILP AR 与 gap

对某个 run 的 400 个测试实例：

    ILP AR = 400 个实例的最优 AR 的平均值
    AR     = 同一批实例上 RL 策略 AR 的平均值
    gap    = 1 − AR / ILP AR

- RL 的 AR 只统计合法放置：超容量或违反隐私冲突的那一步放置不计入利用率，也不计入"已使用 ECU"；Mask EXIT 后未放置的服务同样不计入。所以 RL 的 AR 与 ILP AR 用的是同一套约束，可以直接比较。
- 报告中的表格对各种子的 gap 再取均值 ± 标准差。
- ILP AR 是同一实例在全部约束下能达到的最大值，所以没有违约的 RL 策略在任何单个实例上的 AR 都不会超过该实例的 ILP AR。

## 6. 无约束目标 AR_obj 不能与 ILP AR 比较

v6.0.1 无约束版本的奖励 AR_obj 把违约放置也计入，并把每个 ECU 的利用率截断到 1。不考虑约束时，把服务尽量堆到少数 ECU 上就能让每个 ECU 都饱和，AR_obj → 1。它不受第 1 节的约束 2、4 限制，因此不是同一个优化问题，AR_obj 高于 ILP AR 没有意义。

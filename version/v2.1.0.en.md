# v2.1.0

## Background

v2.0.0 confirmed that best-of-N raises lt/ppo_mask's success_rate from 52.5% at N=8
to 95% at N=1024 — so for almost every test scenario the trained stochastic policy
already contains "successful behaviour" in its sampling distribution; it is just not necessarily picked at N=1 (deterministic / single sample).
This finding leaves an obvious follow-up question: **best-of-N only trades
inference-time compute (many retries) for success rate; training itself is unchanged** — if a
deployment really gets only one try (retries have a real cost), this scheme cannot be used.

So the natural question: can the "successful paths that only retries hit" be trained into the policy itself,
so that it is more likely to get it right at N=1?

## Change in this version: Self-Imitation / Expert Iteration fine-tuning prototype

New [src/scripts/self_imitation_finetune.py](../scripts/self_imitation_finetune.py),
following the standard recipe in the RL/LLM literature (Expert Iteration / Self-Imitation Learning /
Rejection Sampling Fine-tuning; STaR on the LLM side uses the same mechanism).
The repository previously used it only on "ILP expert trajectories" (the BC warm start of `src/shared/bc_pretrain.py`);
this time it is **the same BC supervised-learning mechanism, fed with the policy's own
successful trajectories**:

1. For each of the `TRAIN_SCENARIOS` (160), sample up to N=64 times with the current policy
   (`deterministic=False`) and keep the first fully successful trajectory ((obs, mask, action)
   sequence); scenarios that never succeed contribute no data.
2. Fine-tune on all collected successful trajectories with `src/shared/bc_pretrain.py::pretrain_actor_critic`
   (the same function originally used for the ILP-expert BC warm start) — essentially the policy
   imitates its own highlights.
3. After fine-tuning, re-evaluate N=1 (deterministic) and N=8 on the test set to see whether the single-try success rate really
   goes up.
4. Repeat 3 rounds (sample → BC fine-tune → evaluate) to see whether it keeps improving or saturates quickly.

A smoke test (5 train / 5 test scenarios, N=8, 2 epochs) verified the pipeline:
after fine-tuning, N=8 success_rate 0.80 → 1.00 (sample too small to conclude anything; it only verifies
the code path). The full run (160 training scenarios, N=64, 10 epochs, 3 rounds) has started in the background,
reusing the v1.2.4 seed=42 model (`0e1a36bb_bc/model_0e1a36bb_bc_v1.2.4`).

### Known limitations

- The 2 scenarios that "cannot be placed even with N=8192" (idx=26/32 in [v2.0.0_scenario_detail.md](v2.0.0_scenario_detail.md))
  have no successful trajectory to sample, so this method cannot help them — self-imitation
  can only turn "can succeed but needs luck" into "succeeds more easily"; it cannot rescue scenarios it never wins.
- It is fine-tuning, not training from scratch — the converged v1.2.4 model is
  tuned further, not replaced.
- Only validated on `lt/ppo_mask`; `ppo_lagrangian` / other algorithms are not covered.
- The BC fine-tuning learning rate, epochs and per-round sample N are first-try initial values, untuned.

## Results (v1: pure BC fine-tuning, negative result)

The full run (160 training scenarios, N=64, 10 epochs/round, 3 rounds) finished:

| | N=1 (deterministic) success_rate | N=8 success_rate |
|---|---|---|
| Baseline (before fine-tuning) | 0.425 | 0.525 |
| after round 1 | 0.350 | 0.500 |
| after round 2 | 0.300 | 0.575 |
| after round 3 | 0.300 | 0.625 |

**The core hypothesis fails, and in the opposite direction**: the N=1 deterministic single-try success rate not only does not improve,
it decreases monotonically (42.5%→30%); N=8 rises slightly above baseline (52.5%→62.5%),
but that is just "the retry mechanism still working", unrelated to the goal of "training successful trajectories into the policy".

Diagnosis: the pure supervised BC loss (`-log_prob(self-sampled successful action)`) pulls the policy's action
distribution hard towards a small set of successful trajectories (155/160 scenarios, only 1 per scenario) — BC training accuracy
rose from 92.6% to 97%+, showing the policy overfitting this narrow set; the side effect is compressing
the policy's exploration/randomness, which hurts generalization to other test scenarios. This is a known pitfall of self-imitation
methods: pure BC easily collapses the distribution; the standard practice (Expert Iteration literature)
never does BC alone — BC must be followed by RL training with the real reward, so that the reward
signal corrects the collapse caused by BC.

## Results (v2: light BC fine-tuning + RL recovery, in progress)

New [src/scripts/self_imitation_finetune_v2.py](../scripts/self_imitation_finetune_v2.py),
fixing v1:
- BC epochs from 10 to 3, learning rate from 3e-4 to 1e-4 (smaller collapse per step).
- **After each BC round, add `model.learn(200_000 steps)` of real PPO training** (same
  reward/GAE, without `RA.P4Callback` — that callback writes to
  `results/<scenario>/ppo_mask/.progress.json`, the same file the live dashboard
  reads for "current training progress", and would interfere with the display of the official training; instead a
  local callback `_SilentEpisodeTracker` only records episode AR and does not touch the shared progress file).
- `results.json` is now written to a separate pseudo-algorithm directory
  `results/<branch>/lt/ppo_mask_selfimit/<exp_id>/` (not `lt/ppo_mask/`),
  so it shows as its own row on the dashboard without overwriting the result card of the official `lt/ppo_mask`
  training.

A smoke test (5 train / 5 test scenarios, N=8, 2 epochs, 2000 RL-recovery steps) verified the pipeline;
`results.json` is written correctly and readable via `/api/history/lt/ppo_mask_selfimit`.
The full run (3 rounds, N=64, 160 training scenarios, 200k RL-recovery steps per round) has started in the background; results pending.

## Results (v2 final: 6 rounds, N=1024 sampling + evaluation)

At the user's request, sampling N and evaluation N were both set to 1024 (the earlier 3-round v2 experiment used N=64 sampling and
N=8 evaluation, the wrong scale, not directly comparable with v2.0.0's best-of-N conclusion), rerun for 6 rounds:

| | N=1 (deterministic) | N=8 | N=1024 |
|---|---|---|---|
| Baseline | 0.425 | 0.525 | 0.900 |
| round 1 | 0.350 | 0.650 | 0.850 |
| round 2 | 0.375 | 0.625 | 0.900 |
| round 3 | 0.375 | 0.525 | 0.900 |
| round 4 | 0.375 | 0.675 | 0.900 |
| round 5 | 0.350 | 0.625 | 0.900 |
| round 6 | 0.300 | 0.575 | 0.900 |

**No improvement on any of the three, a clear negative result**:
- N=1: none of the 6 rounds returns to the baseline 0.425; round 6 is the lowest of all (0.300).
- N=8: fluctuates between 0.525~0.675 without a monotone trend, essentially noise.
- N=1024: stable at 0.85~0.90 throughout; fine-tuning neither breaks nor raises this ceiling.

**Conclusion**: with both implementations, pure BC fine-tuning (v1) and BC + RL recovery (v2), regardless of strength or the RL
correction step, the N=1 single-try success rate never exceeds the baseline — the problem is not something simple tuning like "not enough RL-recovery steps"
can fix; the route of "training best-of-N's successful experience into the single-try policy"
with the current implementation (periodic batch collection + separate BC/RL stages) is **validated as a
negative result; further investment in this direction is not recommended**. See "Improvements not adopted" below for the diagnosis.

## Improvements not adopted (recorded, not implemented in this version)

Two possible root causes of this implementation were identified in discussion, but v2.2.0
(making AR the optimization target) was judged higher priority, so they were not pursued in this version:

1. **The sampling strategy itself is flawed**: `collect_self_imitation_data` "stops at the first
   successful trajectory among N", rather than "picks the trajectory with the highest AR among N" — the imitation target
   has unknown quality, so the mechanism never aligns with "which trajectory should be learned".
2. **A more thorough architecture would be continuous Self-Imitation Learning** (Oh et al.
   2018), keeping a cache of the highest return seen per scenario/state and spreading the signal "exploit high-return trajectories"
   continuously into an auxiliary loss of the normal training loop, instead of, as in this version, stepping out every
   200k steps for a separate three-stage N=1024 batch sampling + BC + RL that fight each other.

# v1.1.0

## Background

Until now, `step()` in every `scenarios/{eq,gt,lt}/{base,ppo,ppo_mask,ppo_lagrangian,ppo_opt,dqn,ddqn}/env.py` (20 files) returned a step-wise (dense) reward: a positive reward for the resource-utilization increment (ru) at each step, a fixed penalty for violations, plus a terminal bonus only at the last step. Such dense shaping couples the gradient of intermediate steps only weakly to the final placement outcome (whether everything was placed legally), and some files (e.g. the `ppo` family) did not correctly check whether a violation had occurred before giving the terminal bonus.

## Changes in this version

### Reward becomes purely terminal and sparse (20 `env.py`)

- Non-terminal steps (`done=False`): reward always `0.0`.
- Terminal step (`done=True`, i.e. `self._step >= self.M`):
  - episode fully successful (no capacity/conflict or any other violation): `reward = +self.M`
  - otherwise: `reward = -self.M`
  - `M` is the number of services to place in the scenario (the environment attribute `self.M`), so the success/failure magnitude scales with the scenario size.
- The early-termination branch for a failed repair in the `ppo_opt` family also becomes `-float(self.M)`.
- The existing violation counters, `info` dict and action-masking logic of each file are unchanged; only the reward computation/return value changes.

### Advantage computation

- No hand-written GAE was added — PPO/MaskablePPO training keeps stable_baselines3's `RolloutBuffer.compute_returns_and_advantage` (standard GAE, `gamma=0.99`, `gae_lambda=0.95`, see `scenarios/*/ppo_mask/config.py`); GAE propagates the sparse terminal reward back to the advantage of every step in the episode via `gamma`/`lambda`, so neither `shared/adaptive_ppo.py` nor any training loop needs changes.

### Fixed along the way

- The `ppo` family (eq/gt/lt) used to add a positive terminal bonus without checking for violations; it now decides success/failure from `total_viol`.

### Version number

- The default `VERSION` in `shared/paths.py` goes from `0.3.2` to `1.1.0`.

## Notes

- This is a structural reward change: historical checkpoints and this version's environment no longer share the reward scale, and training curves (especially `ep_rew_mean`) cannot be compared directly with older versions; retraining and re-evaluation are recommended.

## Results (2026-07-11, exp_id=d3c9cf09, full run of eq/gt/lt × 6 algorithms)

The results are **not good**: of the 18 models, only `ppo_mask` (and `ppo_lagrangian` in some scenarios) reaches success_rate 1.0 with AR better than or close to the old version under the new purely terminal sparse reward; the other algorithms without action masking (`ppo`, `ppo_lagrangian` (eq/lt), `ppo_opt`, `dqn`, `ddqn`) drop to success_rate 0 (or very low); their AR numbers are not low, but they are computed while almost everything violates and do not reflect real scheduling quality.

Diagnosis: a sparse terminal reward hurts algorithms without action masking much more — early in training they almost never place many consecutive steps legally, so nearly every episode in 5M steps gets `-M`, and the reward signal carries almost no gradient to tell good from bad policies (the classic "sparse reward + no prior constraint → exploration cannot learn"). `ppo_mask` removes illegal actions via action masking, so almost every episode succeeds naturally; it actually benefits from the new reward and gets a clean `+M` signal.

Conclusion: the purely terminal sparse reward + GAE back-propagation **only works for algorithms that already have action-masking constraints (ppo_mask, ppo_lagrangian in some scenarios)**; it is not suitable for unconstrained exploring algorithms (plain ppo/dqn/ddqn/ppo_opt), which need extra shaping / longer training / behaviour-cloning pre-training to ease exploration. The code is not rolled back in this version; the phenomenon is only recorded, and a later version will decide whether to use per-algorithm reward schemes.

## Methodology note: averaging the ILP AR across scenarios (eq/gt/lt) is meaningless

The three scenarios eq/gt/lt differ in N (number of ECUs), M (number of services) and capacity distribution, so their ILP-optimal ARs are on different scales (measured ILP mean AR this time: eq=0.5321, gt=0.6337, lt=0.7213). Averaging the AR or AR gap over the three scenarios mixes the optimal baselines of three problems of different size; the resulting "overall average AR/gap" has no real meaning and does not show an algorithm's true gap to the ILP in any scenario.

Comparisons should always be presented **per scenario** (AR vs that scenario's own ILP AR, gap = ILP_AR − algorithm_AR), never aggregated into a single cross-scenario average. The current aggregation in `scripts/run_paper_verification.sh` is correct (rows per scenario/algo, no cross-scenario average); if an "overall" metric is ever added to the paper or the dashboard, use a relative gap (e.g. gap/ILP_AR normalized) instead of an average of absolute AR.

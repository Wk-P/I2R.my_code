# v1.2.4

## Background

All lt success_rate/AR numbers so far came from a single TRAIN_SEED=42, with no idea of the
run-to-run variance — the judgement "success_rate is stuck at some number" does not hold if
different seeds can already differ by twenty or thirty percentage points, and the effect of any later training-side change
cannot be told apart from seed luck. The training curves also showed signs of instability, a sudden drop mid-training
followed by recovery (see the v1.2.3 background); a multi-seed reproduction is the first step in diagnosing both problems,
and it needs no change to any training/model logic.

## Changes in this version

### 1. Experiment-process watchdog ([app/backend/monitor.py](../app/backend/monitor.py))

A separate long-running process that polls `ps` + each scenario's `.progress.json` every 30 s
and records across polls whether the step count is changing — `/api/progress` itself is stateless, and a single request
cannot tell "process alive but not progressing"; only an independent process with memory can track this.

- Rules: the same pid with no step change for 15 minutes → `stuck`; a live process that has not written even its
  first `.progress.json` after 15 minutes → also `stuck`.
- State is written to `app/backend/monitor_state.json` (gitignored); `/api/progress`
  reads it and adds `monitor_status` / `stalled_seconds` to its existing fields.
- The frontend [ProgressPanel.vue](../app/frontend/src/components/ProgressPanel.vue)
  shows a `stuck` badge next to the card title (`watchdog not running` when the watchdog is not started).
- Kept alive with systemd `Restart=always` (`~/.config/systemd/user/my-code-monitor.service`,
  the same mechanism as the existing `my-code-panel.service`), already `enable --now`, so it needs no
  manual start and does not depend on the life of a terminal/SSH session.
- **Experiments of every future version run under this watchdog**; it is not a one-off change
  of this version — this entry only records that it was introduced in v1.2.4.

### 2. lt/ppo_mask multi-seed diagnosis ([src/scripts/multiseed_lt_ppomask.sh](../scripts/multiseed_lt_ppomask.sh))

- With the default hyper-parameters of the current config.py (no change to training logic), `TRAIN_SEED` is set to
  42/1/2/3/4 and `scenarios/lt/ppo_mask/run_all_bc.py` is run five times in sequence.
- `TRAIN_SEED` controls both the train/test split (80/20) and the RL training randomness (see
  `scenarios/lt/ppo_mask/config.py`), so each seed is an independent end-to-end
  reproduction, not just the same data with another random seed.
- After the five runs the summary is written to
  `results/paper-verfication/lt/ppo_mask/v1.2.4_multiseed_summary.txt`,
  recording each seed's `success_rate`/`ar_mean`/`ar_std`, and an email notification is sent.

### Version number

- `CURRENT_VERSION` in `src/shared/version_config.py` goes from `1.2.3` to `1.2.4`.

## Results

All 5 seeds finished (5,000,000 steps × 5); summary in
[v1.2.4_multiseed_summary.txt](../results/paper-verfication/lt/ppo_mask/v1.2.4_multiseed_summary.txt):

| seed | exp_id | success_rate | ar_mean | ar_std |
|---|---|---|---|---|
| 42 | 0e1a36bb | 0.650 | 0.6214 | 0.0738 |
| 1  | 63faab82 | 0.575 | 0.6422 | 0.0761 |
| 2  | 12fc7eef | 0.675 | 0.6480 | 0.0790 |
| 3  | 8e6a5a00 | 0.625 | 0.6577 | 0.0861 |
| 4  | 465653ac | 0.675 | 0.6467 | 0.0670 |

- success_rate mean ≈ 0.640, range 0.575~0.675 (about 10 percentage points); the run-to-run
  variance is not large — "lt success_rate won't go up" is a systematic bottleneck, not one unlucky seed.
- The training curves (e.g. [0e1a36bb_bc/training_curve.png](../results/paper-verfication/lt/ppo_mask/0e1a36bb_bc/training_curve.png)) show `valid_placed` now really converging close to
  M=15 (5M steps in effect), so v1.2.3's worry of "not trained enough" is resolved; the sudden drop around ~1.4M steps
  still reproduces on seed=42, but it is small and self-healing, not the main cause.
- After convergence the episode AR levels off at ~0.65, below the ILP optimum 0.7213 — this is "fits but
  not packed well enough" (suboptimal); success_rate stuck at 57.5%~67.5% is "some scenarios cannot place all 15 services even with 8
  best-of-N retries" (infeasible); these are different problems,
  and the low success_rate is the real bottleneck to solve now.

## Alignment problem found afterwards (fixed while closing v1.2.4)

An audit of `scenarios/{eq,gt,lt}/{ppo,ppo_mask,ppo_lagrangian,ppo_opt,dqn,ddqn}/config.py`
found that `TOTAL_STEPS` of `lt/ppo`, `lt/ppo_opt`, `lt/dqn`, `lt/ddqn` called
`get_total_steps()` without the `scenario=` argument — so the `SCENARIO_TOTAL_STEPS` override table introduced in v1.2.3
never applied to these 4 algorithms (even adding entries later would not work, because the lookup requires a
`(scenario, algo)` pair, and without the scenario it never matches). Fixed uniformly to pass `scenario=ROOT.parent.name` (consistent with
`ppo_mask`/`ppo_lagrangian`), also for eq/gt (no behavioural
change for eq/gt now, since `SCENARIO_TOTAL_STEPS` has no entries for them; it only unifies the entry point
so no algorithm is missed when entries are added later).

- best-of-N evaluation (`EVAL_BEST_OF_N`/`n_samples` resampling) is still only wired into
  `ppo_mask`/`ppo_lagrangian`; `ppo`/`ppo_opt`/`dqn`/`ddqn` are not covered yet —
  consistent with v1.2.2's notes; the scope was not extended this time and is left for a later version.

## Notes

- Only `lt/ppo_mask` is covered; `ppo_lagrangian` and the other algorithms have not been run with multiple seeds.
- If success_rate varied a lot across the 5 seeds, the conclusion "lt success rate won't go up"
  would have to be restated as a range rather than a point; if the variance is small, it really is a systematic bottleneck,
  and the next step follows the direction in v1.2.3's notes (locate the cause of the sudden drop → targeted convergence training).

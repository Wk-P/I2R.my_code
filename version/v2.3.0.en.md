# v2.3.0

## Background

While investigating "lt/ppo_mask success_rate is very low again" (v2.2.0's `e251a0fb_bc` reached only
47.5%), the first suspicion was that the state design lacked information (the policy could not learn "will this step
leave no way forward later"), so `env.py` got an explicit bottleneck-risk feature
(`bottleneck_risk`, see below). But an isolated control experiment unexpectedly showed that the main factor
is not the state design but **BC pre-training**.

## Isolated experiment results (the same 40 standard held-out test scenarios, best-of-8)

| Setting | Steps | BC pre-training | bottleneck feature | success_rate | AR mean |
|---|---|---|---|---|---|
| Baseline `e251a0fb_bc` (original v2.2.0) | 5,000,000 | yes | no | 47.5% | 0.6325 |
| No BC, same steps | 5,000,000 | no | no | **70.0%** | 0.6347 |
| Steps cut to 500k | 500,000 | no | no | 80.0% | 0.6005 |
| Add bottleneck feature | 500,000 | no | yes | 85.0% | 0.6199 |

Variable by variable:
- **No BC (same 5M steps)**: success_rate 47.5%→70.0% (**+22.5pp, the largest of the four variables**), AR almost unchanged (0.6325→0.6347). The BC warm start (behaviour cloning of ILP expert trajectories) is a net negative under v2.2.0's AR-proportional terminal reward, not the expected "faster convergence".
- **Steps 5M→500k (both without BC)**: success_rate +10pp more, but AR drops 0.03 — training time is a real trade-off (the longer it trains, the more it "pushes" into dead ends on a few high-risk scenarios, but with higher quality when it succeeds), not monotonically "more training is better".
- **Add bottleneck feature (on top of 500k)**: success_rate +5pp and AR slightly up, both in the same direction, but from a single training run without multiple seeds, so not conclusive.

## Decision: BC pre-training permanently disabled

**The conclusion is settled and needs no further validation** — BC pre-training is a net negative under the current reward; flows that depend on a BC warm start,
such as `run_all_bc.py` / `scripts/self_imitation_finetune*.py`, are no longer used as the
standard training path (historical results and scripts are kept, not deleted, just not adopted in new experiments).
From now on lt/ppo_mask (and the other scenario/algorithm combinations pending validation) use `run_all.py`
(without the BC step) as the standard training entry point.

**Open issue for later validation**: this conclusion has only been validated on one (scenario, algorithm) combination,
`lt/ppo_mask`; whether the `eq`/`gt` scenarios and the other algorithms
(`ppo_lagrangian`/`ppo_opt`/`dqn`/`ddqn`) show the same negative BC effect has not been tested.

## New branch: `add_states`

The state design (bottleneck_risk feature) was not disproved, it just contributes less than expected,
and is still worth studying — a new branch `add_states` was opened (from the clean no-BC baseline of this version);
later observation-design experiments are done there, keeping the main line clean. Changes already on that branch:
the observation in `scenarios/lt/ppo_mask/env.py` grows from `5N+6+2M` to `5N+7+2M`
dimensions, adding `bottleneck_risk` (the share of remaining services with valid_ecu_count<=1,
an aggregate "approaching a dead end" signal).

**Next steps**:
- On the no-BC baseline (5M steps), run a control with the bottleneck feature to confirm whether the +5pp
  holds at full training length (so far only validated at 500k steps).
- Repeat with multiple seeds to quantify the variance of the current single run.
- Check whether the BC-disable conclusion also holds for eq/gt and the other algorithms.
